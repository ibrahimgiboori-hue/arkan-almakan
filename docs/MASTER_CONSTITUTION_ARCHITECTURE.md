# الدستور المعماري الأعلى — أركان المكان

## المبدأ الحاكم

النظام يُبنى مثل مبنى له أعمدة حاملة ثابتة وغلاف قابل للاستبدال.

- الأعمدة الحاملة = البيانات، العلاقات، الصلاحيات، المعاملات، الحالات، قواعد الحساب، سجل التدقيق، العقود البرمجية المشتركة.
- الغلاف = شكل الواجهة، الألوان، القوائم، مواضع العناصر، البطاقات، الجداول المرئية، قوالب المطبوعات، وطريقة العرض.

يجب أن يكون من الممكن خلع الغلاف واستبداله بغلاف آخر دون التأثير على البيانات أو الوظائف أو قواعد العمل.

## قرار الاعتماد خلال مرحلة التوحيد

الواجهة السوداء الحالية ومحتوياتها ونظام المطبوعات والضبط الحالي هي **الغلاف الرسمي المعتمد والمجمّد وظيفياً وبصرياً خلال مرحلة توحيد البرنامج**.

حتى اكتمال التوحيد:
- لا يستبدل الغلاف الحالي ولا يعاد تصميمه كلياً.
- لا يغير تعديل داخلي هوية الغلاف أو بنية التنقل أو نظام المطبوعات إلا لإصلاح خلل أو تنفيذ مطلب صريح مع الحفاظ على العقود المشتركة.
- أي مكون جديد يجب أن يندمج مع الغلاف الحالي من خلال العقود والتوكنز والمكونات المشتركة، لا بتصميم أو CSS أو منطق مستقل.
- الأولوية الآن لفصل القلب والعقود المشتركة عن الغلاف وإزالة التكرار والترقيعات من داخل الصفحات.

بعد اكتمال توحيد القلب والعقود والمكونات، يجوز إدخال **حزمة واجهة/Theme جاهزة واحدة** وتفعيلها على كامل البرنامج من نقطة مركزية، بشرط التزامها بعقود العرض الموحدة. لا يجوز أن يتطلب تغيير الواجهة ترحيل بيانات أو تعديل قواعد الأعمال أو إعادة كتابة المعاملات.

## الطبقات الأربع

### 1. Core / القلب
لا يعتمد على شكل الواجهة أو قالب الطباعة.
يشمل:
- مخطط البيانات والعلاقات.
- القواعد الحسابية.
- حالات المعاملات والانتقالات المسموحة.
- الصلاحيات والنطاقات.
- قواعد الحضور والأجور والإجازات والمطالبات وغيرها.
- سجل التدقيق والتاريخ.

### 2. Application Contracts / العقود المشتركة
هي الواجهات البرمجية التي تتعامل معها كل الشاشات والمطبوعات.
- تعريف موحد للحالات.
- تعريف موحد للإجراءات.
- تعريف موحد للحقول والكيانات.
- خدمات موحدة للقراءة والكتابة والحساب.
- لا يجوز لصفحة اختراع نسخة محلية من قاعدة موجودة هنا.

### 3. Presentation Shell / الغلاف المرئي
قابل للاستبدال بالكامل بعد اكتمال مرحلة التوحيد.
- App Shell.
- Design Tokens.
- Components.
- Navigation.
- Tables / Cards / Forms.

الواجهة السوداء الحالية هي الغلاف المعتمد والمجمّد الآن، وليست جزءاً من منطق النظام.
أي واجهة مستقبلية يجب أن تستهلك نفس العقود دون إعادة كتابة الوظائف.

قاعدة إلزامية: صفحات البرنامج لا تعرف ألوان الهوية أو مقاسات التحكم أو شكل البطاقات مباشرة؛ تستدعي Tokens/Components مركزية. والهدف أن تغيير Theme مركزي واحد ينعكس على جميع كيانات البرنامج.

### 4. Print Shell / غلاف المطبوعات
قابل للاستبدال بالكامل بعد اكتمال التوحيد دون تغيير المعاملة.
- Letterhead.
- Header / Footer.
- Margins.
- Fonts.
- Table layout.
- Signatures / stamps.

المعاملة تنتج Document Model موحداً، ثم يقوم قالب الطباعة بعرضه.
لا يجوز أن يعيد المطبوع حساب قيمة أو يقرر حالة معاملة.

خلال مرحلة التوحيد، نظام المطبوعات والهوامش والليترهيد والجودة الحالي معتمد ولا يستبدل. التطوير يركز على جعل جميع المطبوعات تستهلك Print Contract وDocument Model مركزيين حتى يمكن لاحقاً تبديل قالب المطبوعات على مستوى البرنامج كله دفعة واحدة.

## قاعدة المكونات

كل مكون يصنف إلى:

1. Load-bearing — أساسي/حامل
   - لا يحذف أو يغير عقده إلا بمراجعة أثره على النظام كله.

2. Replaceable — قابل للاستبدال
   - يمكن تغييره أو تطويره أو حذفه إذا حافظ على العقد المشترك.

3. Optional Plugin — اختياري
   - إضافته أو إزالته لا يجب أن تؤثر على سلامة القلب.

## قاعدة منع الترقيع

ممنوع:
- نسخ معادلة داخل صفحة إذا كانت موجودة في محرك القواعد.
- إنشاء ألوان أو حالات أو تسميات موازية إذا كانت موجودة في الدستور.
- ربط منطق الأعمال مباشرة بمكوّن بصري.
- جعل المطبوع مصدراً للحساب أو الحالة.
- كتابة CRUD خاص بكل صفحة إذا كان يمكن توحيده بعقد مشترك.
- إضافة Theme أو CSS محلي يعيد تعريف الهوية العامة لصفحة واحدة.
- بناء قالب مطبوع مستقل لا يمر عبر عقد المطبوعات المركزي.

## اختبار أي تعديل

قبل اعتماد أي تعديل نسأل:

1. هل يمس القلب أم الغلاف؟
2. هل يمكن إزالة المكون دون فقد البيانات أو كسر المعاملة؟
3. هل تغيير التصميم يتطلب تعديل منطق الأعمال؟ إذا نعم فهناك اقتران يجب فكه.
4. هل توجد قاعدة مكررة في أكثر من مكان؟ إذا نعم تنقل إلى الدستور/المحرك المشترك.
5. هل المطبوع يعرض بيانات محفوظة أم يعيد صنعها؟ يجب أن يعرضها فقط.
6. هل المكون الجديد يستهلك العقود والتوكنز المشتركة أم ينشئ جزيرة مستقلة؟ الجزر المستقلة غير مقبولة.

## بوابة تبديل الواجهة مستقبلاً

لا يتم تبديل الغلاف الحالي إلا بعد تحقق الشروط التالية:
- اكتمال توحيد الحالات والإجراءات وقواعد الأعمال الأساسية.
- اعتماد Design Tokens مركزية وعدم وجود ألوان/هوية عامة مكررة داخل الصفحات.
- اعتماد مكتبة مكونات مشتركة للنماذج والجداول والأزرار والحالات.
- اعتماد Navigation/Module Registry مركزي.
- اعتماد Document Model وPrint Contract مركزيين للمطبوعات.
- مرور الوحدات الرئيسية باختبار أن تغيير الغلاف لا يغير البيانات أو الحسابات أو الصلاحيات.

بعد ذلك يمكن استيراد Theme/واجهة جديدة كحزمة واحدة، ربطها بعقود العرض، ثم تفعيلها مركزياً على جميع كيانات البرنامج دون تعديل كل صفحة على حدة.

## الهدف النهائي

يمكن مستقبلاً:
- استبدال الواجهة السوداء بالكامل بواجهة جديدة من نقطة مركزية.
- تغيير شكل كل المطبوعات من مكان مركزي.
- إضافة وحدة جديدة أو إزالتها دون كسر باقي النظام.
- تغيير مكون غير أساسي دون المساس بالأعمدة الحاملة.
- تطوير النظام تدريجياً دون تراكم ترقيعات أو أكواد متوازية.

هذا المستند هو قاعدة معمارية ملزمة لأي تطوير لاحق في أركان المكان.
